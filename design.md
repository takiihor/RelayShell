# RelayShell Design

**Status:** Product / UX / Engineering Design  
**Target:** Android + iOS  
**Primary stack:** Flutter  
**Related specification:** `SPEC.md`

**Implementation update:** The first Conversation Shell is available from POSIX
computer/project pages. It uses a dedicated direct Bash PTY with nonce framing,
bounded memory-only cards, a mobile composer and same-PTY Terminal handoff.
Persistent multiplexer framing, PowerShell integration, disk transcript retention
and physical-device validation remain future work. See README for current limits
and the release checklist for required device checks; the broader design below
remains the target, not a claim that every phase has shipped.

---

## 1. Product Direction

RelayShell is a mobile-first SSH control surface for remote computers, projects, sessions, commands, files, and long-running CLI work.

The product must not become a generic AI chatbot and must not require an LLM to operate the terminal. The default interaction is deterministic and token-free:

```text
Phone
  ↓
RelayShell
  ↓
SSH
  ↓
Remote shell / PTY
```

The user types real shell commands. RelayShell sends those commands directly to the remote shell and renders the resulting stdout/stderr.

RelayShell supports two first-class ways to interact with the same remote shell infrastructure:

1. **Conversation Mode** — a mobile-friendly command/output conversation.
2. **Terminal Mode** — a full interactive xterm-compatible terminal.

Conversation Mode is not an AI mode. It is a presentation layer for a real live shell/PTTY session.

---

## 2. Core Product Principle

Traditional mobile SSH clients usually start with a blank terminal. That is powerful, but on a phone it creates unnecessary friction:

- small terminal text;
- difficult cursor placement;
- awkward command history;
- poor separation between commands and output;
- difficult copying of individual results;
- interactive keyboard controls competing with the phone keyboard.

RelayShell should preserve the power of a real terminal while making ordinary command-line work feel native on a phone.

The preferred model is:

```text
Computer
  ↓
Project / Session
  ↓
Conversation Mode for normal commands and line-oriented agent interaction
  ↓
Terminal Mode when full terminal rendering is required
```

The two modes are views over the same SSH/session infrastructure, not separate products and not separate remote-control protocols.

---

## 3. Information Architecture

Primary navigation remains:

```text
Home
Computers
Projects
Sessions
More
```

When a computer, project, or resumable session is opened, the primary actions should include:

```text
[Shell]      Conversation Mode
[Terminal]   Full Terminal Mode
[Files]
[Commands]
```

On phones, `Shell` should become the preferred default for ordinary command-line work once Conversation Mode is stable. `Terminal` remains immediately available for advanced or full-screen interactive use.

# 4. Conversation Mode

## 4.1 Definition

Conversation Mode presents a remote shell as a sequence of command and output blocks.

Example:

```text
A30 Server                                      ●

You
cd ~/development/hk_live

Shell
~/development/hk_live

You
git status

Shell
On branch main
Your branch is up to date.

Changes not staged for commit:
  modified: lib/...

Exit 0 · 180 ms

You
nvidia-smi

Shell
NVIDIA-SMI ...

Exit 0 · 340 ms

$ Enter command...                           ▶
```

The UI resembles a messaging application, but there is no chatbot model between the user and the shell.

## 4.2 Non-goals

Conversation Mode must not:

- translate natural language into shell commands by default;
- send every command through an LLM;
- consume tokens for normal operation;
- pretend shell output was generated by an assistant;
- replace Terminal Mode;
- break normal shell state such as `cd`, `export`, aliases, shell functions, or activated environments;
- open a new SSH transport for every command.

Optional AI assistance may be added later as an explicit action such as `Ask AI`, but it must remain opt-in and independent from the core shell path.

---

## 4.3 Clean Shell Requirement

Conversation framing requires a known interactive shell environment. Conversation Mode must therefore start from a **clean direct shell PTY**, even when a host or project normally defaults to tmux or Herdr.

This is a deliberate correctness rule.

A persistent Herdr/tmux session may already be inside:

```text
herdr
codex
claude
vim
htop
```

Injecting the Conversation framing protocol into that existing TUI would be unsafe and unreliable. Conversation Mode must not attach blindly to such a session.

The safe flow is:

```text
Open Conversation
      ↓
Clean direct SSH shell/PTTY
      ↓
Conversation framing active
      ↓
User types `herdr ...` / `codex` / another CLI
      ↓
Foreground process receives direct stdin + terminal key sequences
```

The SSH transport is still shared through `ConnectionManager`; only the shell channel is isolated.

This sequence must work as expected:

```bash
cd ~/development/hk_live
export TEST_MODE=1
source .venv/bin/activate
pwd
echo $TEST_MODE
```

Every command must execute in the same shell state until the direct Conversation shell is closed, restarted, or lost.

Do **not** implement Conversation Mode by running each command using a separate SSH `exec` channel. One-shot execution remains useful for saved actions and probes, but it is not the default execution model for the conversation shell.

---

## 4.4 Command / Output Model

Each user shell submission creates a `ConversationCommand` record in memory:

```text
id
raw_command
submitted_at
started_at
completed_at
state
exit_code
working_directory (when known)
output_chunks
interactive_hint
full_screen_detected
process_inputs
```

Recommended command states:

```text
running
completed
interrupted
disconnected
```

A command message and its output belong together visually.

Example card states:

```text
$ git status
● Running
```

then:

```text
$ git status
On branch main
...
Exit 0 · 0.18s
```

A failed command should not be styled as an application failure. It is a normal shell result:

```text
$ cat missing.txt
cat: missing.txt: No such file or directory
Exit 1 · 0.03s
```

---

## 4.5 Command Framing

A normal terminal is an unstructured byte stream. Conversation Mode needs a reliable way to know which output belongs to which submitted shell command.

RelayShell must **not** parse the visible shell prompt to infer command boundaries. Prompts are user-configurable and cannot be considered a protocol.

Instead, Conversation Mode installs lightweight shell framing for supported remote shells. Each submitted command receives a unique identifier and is surrounded by private sentinel markers that are removed before rendering.

Conceptually:

```text
RS_BEGIN:<command-id>
<command output>
RS_END:<command-id>:<exit-code>
```

Requirements:

1. Markers contain a per-session random nonce so accidental collision with program output is extremely unlikely.
2. Marker bytes never appear in the rendered conversation output.
3. The framing mechanism runs the user's command in the current shell so state-changing commands such as `cd` and `export` persist.
4. The user's command remains intentional raw shell input. RelayShell must not silently rewrite its meaning.
5. Multi-line commands remain supported.
6. If framing cannot be safely established for the current shell, the app offers Terminal Mode instead of pretending the stream is reliable.
7. The framing footer must be parsed by the shell **before** an interactive child starts. RelayShell must never queue its own footer/status lines as future PTY stdin where `read`, Herdr, Codex, or another interactive program could consume them as user input.

The POSIX implementation stages the user command with a quoted heredoc, then runs BEGIN → `eval` → status capture → END inside one already-parsed compound shell command.

Regression tests must prove both:

- `cd` / `export` state survives into the next framed command;
- an interactive child blocks for later user input and does not consume RelayShell footer text.

Windows PowerShell support may use an equivalent marker mechanism appropriate to PowerShell semantics in a later phase.

---

## 4.6 Streaming Output

Output streams into the active command card while the command is running.

Do not wait for process completion before showing output.

For example:

```text
$ flutter test
● Running · 14s

00:01 +12 ...
00:04 +58 ...
00:09 +121 ...
```

The running card exposes:

```text
[Stop]   [Open Terminal]
```

`Stop` sends the appropriate interrupt to the active PTY, normally Ctrl+C, rather than disconnecting the entire SSH connection.

Large output uses bounded in-memory rendering. The first implementation caps rendered content per command rather than allowing an unbounded `tail -f` or build log to exhaust phone memory.

Common ANSI control sequences are removed from the conversation text representation. Terminal Mode remains the authority when exact terminal rendering is required.

---

## 4.7 Interactive Agents and Herdr

Conversation Mode must be friendly to interactive coding workflows, especially:

```text
herdr
ctxguard
pi
codex
claude
opencode
gemini
ssh
```

There are two kinds of input while a command is running:

### Human text input

The bottom composer switches from shell-command mode to foreground-process input mode:

```text
$ herdr ...
● Running

› Tell the worker to run tests
```

Submitting that text sends it directly to the active process stdin through the same PTY. It does **not** create another framed shell command.

The conversation may render these human process inputs as right-side bubbles so a Herdr/Codex interaction remains readable.

### Terminal control input

Coding agents and TUIs need exact key sequences, not textual approximations. Conversation Mode therefore reuses the same accessory-key implementation as Terminal Mode.

The compact Conversation shortcut row must always guarantee:

```text
ESC   CTRL   SHIFT   ALT   TAB   /
```

It then appends the user's configured keys in a horizontally scrollable row, commonly including:

```text
↑  ↓  ←  →  ~  |  &  -  _  :  ^C  SCRL↑  SCRL↓
```

Modifier semantics:

- tap CTRL / ALT / SHIFT → arm for next key;
- long press → lock;
- active/locked state is visibly indicated;
- Shift+Tab sends xterm back-tab (`CSI Z`);
- Shift+arrows use xterm modifier parameter 2;
- Shift+`/` produces `?`;
- CTRL/ALT/SHIFT can be combined with the next single character typed on the phone keyboard while an interactive process is active;
- e.g. CTRL then soft-keyboard `b` sends real Ctrl+B to Herdr, not the letter `b` into the composer.

Raw accessory/control sequences are sent directly to the PTY and are not recorded as fake chat messages.

---

## 4.8 Full-screen TUI Detection and Terminal Fallback

Some commands cannot be represented faithfully as conversational text:

```text
vim
nano
htop
top
less
full-screen Herdr panes
other alternate-screen TUIs
```

Conversation Mode does not attempt to recreate a complete terminal emulator inside a message bubble.

The implementation detects common alternate-screen enable sequences such as:

```text
CSI ?1049 h
CSI ?1047 h
CSI ?47 h
```

When detected, the running card prominently offers:

```text
[Open in terminal]
```

The existing process continues. Opening Terminal Mode displays the **same live `TerminalSession` / PTY**. RelayShell must not launch the command or agent a second time.

Heuristics are advisory. The user can always open Terminal manually.

Long-running non-TUI commands such as `tail -f`, development servers, or line-oriented agents can remain in Conversation Mode with `Stop` and `Open Terminal` actions.

---

## 4.9 Returning from Terminal Mode

Conversation Mode and Terminal Mode are two presentations of one live session.

Preferred behavior:

```text
Conversation Mode
      ↓
Open Terminal
      ↓
Same TerminalSession / same PTY
      ↓
Terminal Mode
```

If the user manually types arbitrary unframed shell commands in Terminal Mode, Conversation Mode must not guess how to reconstruct those message boundaries.

Correctness is more important than pretending the transcript is complete.

# 5. Conversation UI Design

## 5.1 Header

Example:

```text
←  HK Live / A30 Server                     ⋮
   A30 Server · shell
```

Header should show:

- host or project name;
- connection/session state where reliable;
- direct-shell/session identity;
- immediate Terminal action.

Avoid oversized hero panels. The command transcript remains the primary content.

---

## 5.2 Command / Agent Composer

Idle shell composer:

```text
┌──────────────────────────────────────────┐
│ $ Enter command...                   ▶   │
└──────────────────────────────────────────┘
```

Foreground-process composer:

```text
┌──────────────────────────────────────────┐
│ › Send input to running process...   ▶   │
└──────────────────────────────────────────┘
```

Requirements:

- multi-line input;
- command history with accessory ↑ / ↓ while at an idle shell;
- cursor movement with ← / → while at an idle shell;
- paste and IME support;
- monospaced command text;
- clear submit affordance;
- no AI wording such as `Ask anything`;
- while a foreground command is active, submit sends text to that process stdin;
- Stop remains separate from Send so the user does not lose the ability to continue a Herdr/Codex conversation.

---

## 5.3 Mobile Accessory Row

Conversation Mode reuses RelayShell's existing `AccessoryKeyboard` and `TerminalInputModifiers` rather than creating a second implementation.

On phones it renders a **single horizontal scrolling row** so the transcript remains visible above the software keyboard.

The accessory row sits above the composer, so it delegates bottom SafeArea handling to the composer to avoid a duplicate system-navigation gap.

Default Terminal rows may remain two rows; Conversation flattens configured keys into one deduplicated row and guarantees its coding-agent essentials.

---

## 5.4 Message Actions

Command bubble actions can include:

```text
Copy
Edit & Run
Run Again
Save Command
```

Output bubble actions can include:

```text
Copy
Select
Share
Open Terminal
```

When output is very long:

```text
Show more
Copy all
Open in Terminal
```

Raw commands typed directly into a live shell are intentional shell input and should not be blocked by a simplistic danger detector. Existing saved-command confirmation rules remain unchanged.

---

## 5.5 History

Conversation history has two distinct concepts:

1. **Live terminal/session buffer** — what belongs to the current PTY.
2. **Local conversation presentation history** — command/output/process-input blocks kept by RelayShell for usability.

The app must not imply that local message history can reconstruct the complete remote process state.

For privacy, command/output history remains local by default and must never be uploaded to a RelayShell cloud service because RelayShell has no required cloud backend.

The first implementation keeps the Conversation transcript in memory only.

---

# 6. Terminal Mode

Terminal Mode remains a complete interactive PTY using the existing xterm-based implementation.

It is required for:

- full-screen TUIs;
- arbitrary cursor movement;
- interactive coding CLIs that depend on exact screen layout;
- editors;
- nested SSH;
- applications that depend on exact terminal escape-sequence behavior.

Conversation Mode is an additional first-class UX, not a replacement for the terminal emulator.

---

# 7. Shared Session Architecture

Do not create a second SSH stack for Conversation Mode.

Current RelayShell already owns:

```text
ConnectionManager
SshConnection
TerminalSession
TerminalManager
SessionLauncher
Multiplexer support
```

Conversation Mode reuses these foundations.

Current first implementation:

```text
ConnectionManager
      ↓
shared SshConnection
      ↓
clean direct TerminalSession / PTY
      │
      ├── xterm Terminal buffer
      ├── presentation-neutral outputStream
      ├── sendText()
      ├── sendRaw()
      └── reconnect/lifecycle
             │
      ┌──────┴─────────┐
      │                │
TerminalScreen   ConversationController
                       │
                 CommandFramer
                       │
                ConversationShellScreen
```

This avoids duplicating authentication, host verification, reconnection, PTY management, or SSH transport code.

A future core refactor may extract an explicit presentation-neutral `InteractiveShellSession`, but that refactor is not required before validating the user-facing Conversation workflow.

# 8. Flutter Structure

Conversation feature directory:

```text
lib/features/conversation_shell/
├── command_framer.dart
├── conversation_controller.dart
├── conversation_models.dart
└── conversation_shell_screen.dart
```

Shared mobile input remains under:

```text
lib/features/terminal/
├── accessory_keyboard.dart
└── terminal_input_modifiers.dart
```

`features/conversation_shell` may depend on `core`, `shared`, and the presentation-neutral interfaces exposed by the terminal/session feature, but core SSH code must not depend on Conversation UI.

---

# 9. Reconnection and Persistence

Conversation Mode currently starts from a direct shell for framing safety.

If the transport drops:

```text
SSH lost
   ↓
active Conversation command → disconnected
   ↓
TerminalSession reconnect logic may restore a fresh direct shell
```

RelayShell must not pretend the foreground direct-shell process survived a dropped SSH session.

If the foreground application is itself persistent — for example Herdr managing a named remote session — that application's own persistence can still be used after reconnecting, but automatic semantic reattachment belongs to a later Conversation-specific recovery design.

---

# 10. Security and Privacy

Conversation Mode inherits RelayShell's existing SSH security model:

- host-key verification remains mandatory;
- changed fingerprints remain blocking;
- credentials remain in platform secure storage;
- no RelayShell cloud relay is introduced;
- terminal output and command text remain between the user's device and remote machine;
- Conversation framing sentinels contain random identifiers but no credentials.

Conversation Mode must never send commands or output to an AI service unless the user explicitly invokes a future AI action.

---

# 11. Testing Strategy

Automated tests should cover at minimum:

1. command framing BEGIN/END parsing;
2. marker split across output chunks;
3. exit-code parsing;
4. `cd` state surviving to the next command;
5. environment variable state surviving to the next command;
6. interactive child waits for later user stdin rather than consuming framing footer text;
7. output truncation limit;
8. ANSI stripping;
9. Ctrl+C interruption;
10. Shift modifier latching;
11. Shift+Tab and Shift+arrow terminal sequences;
12. default accessory rows contain Ctrl, Shift, Tab, `/`, and Ctrl+C;
13. accessory-key touch targets remain mobile-accessible;
14. Conversation accessory row can disable bottom SafeArea when composed above the composer;
15. host/project Conversation entry points always start a clean direct shell;
16. Windows hosts fall back to Terminal Mode until a supported framing implementation exists.

Physical-device release checks must additionally cover Herdr, Codex/Claude/Pi, phone IME behavior, soft-keyboard Ctrl+B, alternate-screen fallback, network loss, and switching to the same live PTY in Terminal Mode.

---

# 12. Implementation Phases

### Phase 1 — Core Conversation Shell

- direct clean shell/PTTY;
- command framing;
- streaming command cards;
- exit status;
- bounded output;
- host/project entry points.

### Phase 2 — Coding-Agent / Herdr UX

- interactive foreground stdin from composer;
- shared accessory keyboard;
- Shift support;
- soft-keyboard modifier interception;
- command history/cursor controls;
- alternate-screen detection;
- same-PTY Terminal fallback.

### Phase 3 — Robustness

- more framing tests across POSIX shells;
- reconnect semantics;
- transcript lifecycle/persistence decision;
- PowerShell framing design;
- richer command actions (copy, re-run, save).

### Phase 4 — Optional AI Assistance

Only after the non-AI shell workflow is stable:

```text
Ask AI
Explain output
Suggest command
```

AI remains explicit and opt-in. Normal RelayShell Conversation use remains token-free.

---

# 13. Acceptance Criteria

Conversation Mode is ready for first release only when all of the following are true:

1. A POSIX Computer or Project can open Conversation Mode directly.
2. Conversation starts from a clean shell even when the host's normal multiplexer is Herdr.
3. `cd`, `export`, and activated environments persist across framed commands.
4. stdout/stderr streams into the active command card.
5. exit code and elapsed time are reported correctly.
6. Ctrl+C interrupts a command without closing the SSH transport.
7. command output is bounded in memory.
8. Conversation always exposes ESC, CTRL, SHIFT, ALT, TAB, and `/` in a compact mobile row.
9. Shift+Tab and Shift+arrow sequences work as real terminal sequences.
10. A running Herdr/Codex/Claude/Pi process can receive human composer text as stdin.
11. Raw accessory-key sequences go directly to the active PTY.
12. CTRL followed by a single soft-keyboard character can generate control input such as Ctrl+B.
13. Interactive programs cannot consume RelayShell BEGIN/END/status protocol text as stdin.
14. Alternate-screen programs are detected and offer same-session Terminal Mode.
15. Opening Terminal during a running Conversation command does not restart the process.
16. Windows hosts remain on Terminal Mode until Conversation framing is explicitly supported.
17. No LLM/API call occurs during ordinary Conversation Mode operation.
18. Existing Terminal Mode continues to work with its configured accessory rows.
19. `flutter analyze` and `flutter test` pass in CI.
20. Physical Android/iOS SSH tests pass the Conversation Mode checklist in `docs/RELEASE_CHECKLIST.md`.
