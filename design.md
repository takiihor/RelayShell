# RelayShell Design

**Status:** Product / UX / Engineering Design  
**Target:** Android + iOS  
**Primary stack:** Flutter  
**Related specification:** `SPEC.md`

---

## 1. Product Direction

RelayShell is a mobile-first SSH control surface for remote computers, projects, sessions, commands, files, and long-running CLI work.

The product must not become a generic AI chatbot and must not require an LLM to operate the terminal. The default interaction is deterministic and token-free:

```text
Phone
  ↓
RelayShell
  ↓
SSH
  ↓
Remote shell / PTY
```

The user types real shell commands. RelayShell sends those commands directly to the remote shell and renders the resulting stdout/stderr.

RelayShell now supports two first-class ways to interact with the same remote shell infrastructure:

1. **Conversation Mode** — a mobile-friendly command/output conversation.
2. **Terminal Mode** — a full interactive xterm-compatible terminal.

Conversation Mode is not an AI mode. It is a presentation layer for a real persistent shell.

---

## 2. Core Product Principle

Traditional mobile SSH clients usually start with a blank terminal. That is powerful, but on a phone it creates unnecessary friction:

- small terminal text;
- difficult cursor placement;
- awkward command history;
- poor separation between commands and output;
- difficult copying of individual results;
- interactive keyboard controls competing with the phone keyboard.

RelayShell should preserve the power of a real terminal while making ordinary command-line work feel native on a phone.

The preferred model is:

```text
Computer
  ↓
Project / Session
  ↓
Conversation Mode for normal commands
  ↓
Terminal Mode when full terminal semantics are required
```

The two modes are views over the same SSH/session infrastructure, not separate products and not separate remote-control protocols.

---

## 3. Information Architecture

Primary navigation remains:

```text
Home
Computers
Projects
Sessions
More
```

When a computer, project, or resumable session is opened, the primary actions should include:

```text
[Shell]      Conversation Mode
[Terminal]   Full Terminal Mode
[Files]
[Commands]
```

On phones, `Shell` should become the preferred default for ordinary command-line work once Conversation Mode is stable. `Terminal` remains immediately available for advanced or interactive use.

# 4. Conversation Mode

## 4.1 Definition

Conversation Mode presents a persistent remote shell as a sequence of command and output blocks.

Example:

```text
A30 Server                                      ●

You
cd ~/development/hk_live

Shell
~/development/hk_live

You
git status

Shell
On branch main
Your branch is up to date.

Changes not staged for commit:
  modified: lib/...

Exit 0 · 180 ms

You
nvidia-smi

Shell
NVIDIA-SMI ...

Exit 0 · 340 ms

$ Enter command...                           ▶
```

The UI resembles a messaging application, but there is no chatbot between the user and the shell.

## 4.2 Non-goals

Conversation Mode must not:

- translate natural language into shell commands by default;
- send every command through an LLM;
- consume tokens for normal operation;
- pretend shell output was generated by an assistant;
- replace Terminal Mode;
- break normal shell state such as `cd`, `export`, aliases, shell functions, or activated environments;
- open a new SSH process for every command.

Optional AI assistance may be added later as an explicit action such as `Ask AI`, but it must remain opt-in and independent from the core shell path.

---

## 4.3 Persistent Shell Requirement

Conversation Mode must run on a persistent SSH PTY or persistent tmux/Herdr-backed session.

This sequence must work as expected:

```bash
cd ~/development/hk_live
export TEST_MODE=1
source .venv/bin/activate
pwd
echo $TEST_MODE
```

Every command must execute in the same shell state until the session is closed, restarted, or lost.

Do **not** implement Conversation Mode by running each command using a separate SSH `exec` channel. One-shot execution remains useful for saved actions and probes, but it is not the default execution model for the conversation shell.

---

## 4.4 Command / Output Model

Each user submission creates a `ConversationCommand` record in memory:

```text
id
raw_command
submitted_at
started_at
completed_at
state
exit_code
working_directory (when known)
output_chunks
```

Recommended command states:

```text
queued
running
completed
failed
interrupted
disconnected
```

A command message and its output belong together visually.

Example card states:

```text
$ git status
● Running
```

then:

```text
$ git status
On branch main
...
Exit 0 · 0.18s
```

A failed command should not be styled as an application failure. It is a normal shell result:

```text
$ cat missing.txt
cat: missing.txt: No such file or directory
Exit 1 · 0.03s
```

---

## 4.5 Command Framing

A normal terminal is an unstructured byte stream. Conversation Mode needs a reliable way to know which output belongs to which submitted command.

RelayShell must **not** parse the visible shell prompt to infer command boundaries. Prompts are user-configurable and cannot be considered a protocol.

Instead, Conversation Mode should install lightweight shell framing for supported remote shells. Each submitted command receives a unique identifier and is surrounded by private sentinel markers that are removed before rendering.

Conceptually:

```text
RS_BEGIN:<command-id>
<command output>
RS_END:<command-id>:<exit-code>
```

Requirements:

1. Markers must contain a per-session random nonce so accidental collision with program output is extremely unlikely.
2. Marker bytes must never appear in the rendered output.
3. The framing mechanism must run the user's command in the current shell rather than a new subshell where practical, so state-changing commands such as `cd` and `export` persist.
4. The user's command remains intentional raw shell input. RelayShell must not silently rewrite its meaning.
5. Multi-line commands must remain supported.
6. If framing cannot be safely established for the current shell, the app must offer Terminal Mode instead of pretending the conversation stream is reliable.

Shell integration should initially target common POSIX shells used over SSH. Windows PowerShell support can use an equivalent marker mechanism appropriate to PowerShell semantics.

---

## 4.6 Streaming Output

Output must stream into the active command card while the command is running.

Do not wait for process completion before showing output.

For example:

```text
$ flutter test
● Running · 14s

00:01 +12 ...
00:04 +58 ...
00:09 +121 ...
```

The running card should expose:

```text
[Stop]   [Open Terminal]
```

`Stop` sends the appropriate interrupt to the active PTY, normally Ctrl+C, rather than disconnecting the entire SSH connection.

Large output must use bounded in-memory rendering. The UI may keep recent visible chunks while persisting or truncating older output according to a documented limit. RelayShell must not allow an unbounded `tail -f` or build log to exhaust phone memory.

---

## 4.7 Interactive and TUI Programs

Some commands cannot be represented well as conversational output:

```text
vim
nano
htop
top
less
ssh another-host
ctxguard
pi
codex
claude
```

Conversation Mode must not attempt to recreate a complete terminal emulator inside a message bubble.

When RelayShell detects that a command has entered an interactive / full-screen terminal state, the UI should present:

```text
$ ctxguard

Interactive terminal session is running.

[Open Terminal]
```

The existing process must continue. Opening Terminal Mode must attach the terminal UI to the **same live PTY/session**, not start the command again.

Detection may use multiple signals:

- alternate-screen-buffer control sequences;
- known interactive command hints;
- terminal mode changes;
- command remaining active without a completion marker;
- explicit user choice.

Heuristics are advisory. The user must always be able to choose `Open Terminal` manually.

Long-running non-TUI commands such as `tail -f`, development servers, or log streams can remain in Conversation Mode as streaming cards with `Stop` and `Open Terminal` actions.

---

## 4.8 Returning from Terminal Mode

Conversation Mode and Terminal Mode should feel like two views of one session.

Preferred behavior:

```text
Conversation Mode
      ↓
Open Terminal
      ↓
Same PTY / same tmux session
      ↓
Terminal Mode
```

Returning to Conversation Mode is safe only when command framing is still synchronized. If the user manually types arbitrary commands in Terminal Mode that bypass Conversation Mode framing, RelayShell must not guess how to reconstruct message boundaries.

In that case it should either:

1. re-establish framing at the next clean shell prompt; or
2. start a new Conversation Mode shell attached to the same project/session context.

Correctness is more important than pretending the transcript is complete.

# 5. Conversation UI Design

## 5.1 Header

Example:

```text
←  HK Live / A30 Server                     ⋮
   ~/development/hk_live · Connected
```

Header should show:

- host or project name;
- connection state;
- current known working directory where reliable;
- persistent-session identity when applicable;
- menu for reconnect, terminal, session info, clear view, and disconnect.

Avoid oversized hero panels. The command transcript should remain the primary content.

---

## 5.2 Command Composer

Bottom composer:

```text
┌──────────────────────────────────────────┐
│ $ Enter command...                   ▶   │
└──────────────────────────────────────────┘
```

Requirements:

- multi-line input;
- command history;
- swipe or buttons for previous/next command;
- paste support;
- monospaced command text;
- clear submit affordance;
- no AI wording such as `Ask anything`;
- input remains available while a previous command is running only when the shell can safely accept additional input.

Recommended accessory row:

```text
ESC  CTRL  TAB  ↑  ↓  |  &  /  ~
```

The existing RelayShell mobile accessory keyboard behavior should be reused rather than duplicated.

---

## 5.3 Message Actions

Command bubble actions:

```text
Copy
Edit & Run
Run Again
Save Command
```

Output bubble actions:

```text
Copy
Select
Share
Open Terminal
```

When output is very long:

```text
Show more
Copy all
Open in Terminal
```

Dangerous-command confirmation behavior from the existing command system should remain available for saved commands. Raw commands typed directly into a live shell are intentional shell input and should not be blocked by a simplistic detector, although optional warning settings may be offered.

---

## 5.4 History

Conversation history has two distinct concepts:

1. **Live terminal/session buffer** — what belongs to the current PTY/tmux session.
2. **Local conversation presentation history** — command/output blocks kept by RelayShell for usability.

The app should not imply that local message history can reconstruct the complete remote process state.

For privacy, command/output history should remain local by default and must never be uploaded to a RelayShell cloud service because RelayShell has no required cloud backend.

A future setting may allow users to disable local transcript retention entirely.

---

# 6. Terminal Mode

Terminal Mode remains a complete interactive PTY using the existing xterm-based implementation.

It is required for:

- full-screen TUIs;
- arbitrary cursor movement;
- interactive AI coding CLIs;
- editors;
- nested SSH;
- applications that depend on exact terminal escape-sequence behavior.

Conversation Mode is an additional first-class UX, not a replacement for the terminal emulator.

---

# 7. Shared Session Architecture

Do not create a second SSH stack for Conversation Mode.

Current RelayShell already owns:

```text
ConnectionManager
SshConnection
TerminalSession
TerminalManager
SessionLauncher
Multiplexer support
```

Conversation Mode should reuse these foundations.

The preferred long-term architecture separates the live PTY transport from presentation:

```text
ConnectionManager
      ↓
SshConnection
      ↓
PtySessionCore / InteractiveShellSession
      │
      ├── stdout/stderr byte stream
      ├── sendText()
      ├── sendRaw()
      ├── resize()
      ├── reconnect()
      └── lifecycle state
             │
      ┌──────┴─────────┐
      │                │
Terminal Adapter   Conversation Adapter
      │                │
xterm Terminal      Command Framer
      │                │
TerminalScreen      ConversationShellScreen
```

This avoids duplicating authentication, reconnection, tmux handling, PTY management, or SSH transport code.

A minimal first implementation may adapt the current `TerminalSession`, but the transport/output stream should ultimately be presentation-neutral.

# 9. Reconnection and Persistence

Conversation Mode must inherit RelayShell's existing connection model:

```text
SSH lost
   ↓
Conversation shows disconnected state
   ↓
ConnectionManager reconnects / user reconnects
   ↓
Persistent tmux/Herdr session reattaches when available
```

If the PTY is successfully reattached and framing can be re-established, Conversation Mode continues.

If a command was running when the network was lost, the UI must not fabricate its result. Mark it clearly, for example:

```text
$ pnpm test
Connection lost while command was running.
Status unknown.
```

For persistent remote sessions, RelayShell may offer `Open Terminal` or `Resume` to inspect the actual process.

---

# 10. Security and Privacy

Conversation Mode inherits the same SSH security model as the rest of RelayShell:

- host-key verification is mandatory;
- changed fingerprints block connection;
- secrets remain in platform secure storage;
- terminal traffic goes directly from phone to the user's machine;
- no RelayShell server is required;
- no command or output is sent to an LLM unless the user explicitly invokes a future AI feature.

The UI must make this distinction clear. Shell output is remote-computer output, not AI-generated content.

---

# 11. Optional AI Assistance — Future Only

AI must not be part of the default Conversation Mode execution path.

If added later, it should be explicitly invoked, for example:

```text
[Explain error]
[Suggest command]
```

or an explicit command such as:

```text
/ai explain the previous output
```

The user should be able to use RelayShell fully with zero LLM configuration and zero token usage.

A suggested command must be shown to the user before execution and must never silently become shell input.

---

# 12. Accessibility and Mobile Behavior

Conversation Mode should improve mobile usability over a traditional terminal:

- minimum touch targets appropriate for Android/iOS;
- Dynamic Type / text scaling without destroying command layout;
- monospaced text for commands and output;
- selectable output;
- screen-reader labels that distinguish `command`, `output`, `running`, and `exit code`;
- landscape support;
- external keyboard support;
- IME-safe composer behavior;
- bottom composer must stay above system navigation and software keyboard insets.

---

# 13. Testing Requirements

Conversation Mode requires tests beyond ordinary widget snapshots.

## 13.1 Command framing tests

Verify:

- unique begin/end markers;
- markers are stripped from rendered output;
- exit codes map to the correct command;
- output split across arbitrary network chunks still frames correctly;
- multiple commands cannot leak output into each other's cards;
- malformed or missing markers fail safely;
- marker-like user output does not collide with real framing tokens;
- UTF-8 and CJK output survive chunk boundaries.

## 13.2 Shell-state tests

Against a real or test SSH shell, verify that sequential conversation commands preserve:

```text
cd
export
source / activation
shell functions
working directory
```

## 13.3 Streaming tests

Verify:

- output appears before command completion;
- Ctrl+C interrupts the active process without closing shared SSH transport;
- bounded buffers prevent unlimited memory growth;
- `tail -f` and development-server style commands can remain active;
- disconnect while running produces an unknown/disconnected result rather than a false success/failure.

## 13.4 Terminal handoff tests

Verify:

- interactive/TUI detection exposes `Open Terminal`;
- switching to Terminal Mode does not restart the command;
- the same PTY/session continues;
- tmux/Herdr persistent sessions remain resumable after network interruption.

## 13.5 Device tests

Physical Android and iOS testing must include:

- software keyboard open/close;
- accessory keys;
- long output scrolling;
- copy/select;
- background/foreground reconnection;
- mobile network changes;
- portrait/landscape switching;
- system navigation inset behavior.

---

# 14. Implementation Sequence

Recommended implementation order:

### Phase 1 — Session seam

- Extract or expose a presentation-neutral PTY/session byte stream.
- Preserve all existing Terminal Mode behavior.
- Add tests proving terminal regressions have not been introduced.

### Phase 2 — Conversation shell core

- Add `ConversationSession` and message models.
- Add deterministic command framing.
- Support persistent shell state.
- Stream output and capture exit status.
- Implement interrupt/cancel.

### Phase 3 — Mobile Conversation UI

- Command composer.
- Command/output bubbles.
- running/completed/failed/disconnected states.
- copy, rerun, edit-and-run, save-command actions.
- host/project/session header.

### Phase 4 — Terminal handoff

- Detect alternate-screen / interactive states.
- Open existing live PTY in Terminal Mode.
- Define safe return-to-conversation behavior.

### Phase 5 — Persistence and polish

- Local transcript retention policy.
- large-output handling.
- accessibility.
- physical-device testing.
- update `SPEC.md` and release checklist to make Conversation Mode a release-gated feature.

---

# 15. Acceptance Criteria

Conversation Mode is ready when all of the following are true:

1. A user can connect to an existing RelayShell host and open `Shell` without configuring an LLM.
2. Typing `pwd`, `cd`, `export`, `git status`, `docker ps`, `nvidia-smi`, etc. sends the exact intended shell input to the remote machine.
3. The shell state persists across messages.
4. Each command's output is visually grouped with that command.
5. Output streams while the command runs.
6. Exit code and runtime are shown when known.
7. Ctrl+C can interrupt a running command.
8. Long-running output does not grow phone memory without bound.
9. Interactive/TUI programs can move into the existing Terminal Mode without restarting the process.
10. Reconnection works with existing RelayShell persistent-session behavior.
11. Conversation Mode reuses RelayShell SSH authentication, host verification, connection management, projects, sessions, and multiplexer support.
12. Normal usage consumes zero LLM tokens.
13. Terminal Mode remains fully functional and first-class.

---

## 16. Product Summary

RelayShell should not create a second chatbot application.

The product should evolve into a mobile SSH client with two complementary interfaces over the same remote shell:

```text
                 RelayShell
                     │
              Existing SSH Core
                     │
             Persistent PTY/Session
                ┌────┴────┐
                │         │
        Conversation    Terminal
            Mode          Mode
                │         │
        command/output   full xterm
          messages       interaction
```

The central idea is simple:

> **Conversation Mode makes the terminal easier to use on a phone without putting AI between the user and the shell.**
